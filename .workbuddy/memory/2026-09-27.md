## 01:10–01:40 SettingsCard 窄宽度无上下间距 / 反馈图标不在按钮内

**问题 1：宽度小时 SettingsCard 内容上下没间距**

两个原因叠加，都靠可视树探针实测确认（临时 `__LayoutProbe.cs`，用完即删）：

1. **照抄模板的 `Padding="16,0"`** → 上下 0。宽度大时内容只有一行、`MinHeight=70`
   撑着所以看不出来；宽度 < `SettingsCardWrapThreshold`(476，无图标 286) 时控件
   进入 `RightWrapped` 视觉状态，`PART_ContentPresenter` 从 Row0/Col2 移到
   **Row1/Col1**（换到 Header 下面），卡片变高，上下 padding 又是 0 → 内容贴边。
   实测：'导航栏位置' 卡 w=320 时 `padding=16,0,16,0`, h=77.3，content 在 row=1。
   改成 `.Padding(16, 16)` 后 `padding=16,16,16,16`, h=109.3 ✓。
2. Toolkit 的默认值（UWP 包 8.2）是 `SettingsCardPadding = 16,16,4,16`（**右只有 4**），
   `MinHeight` 默认 68。展开区里 item 卡片自带 `58,8,44,8`（左缩进 + 上下 8）。

**注意**：`SettingsExpander` 的 `Padding` **只作用于展开区**（模板里
`ExpanderContent Padding="{TemplateBinding Padding}"`），header 那张卡的 padding 是
模板写死 `SettingsExpanderHeaderPadding=16,16,4,16`。所以 Expander 不需要改 padding，
改了只会让展开区更缩进。
另：Expander 自身 w=320，但内部 header card 只有 277.3（差 42.7）——是 Expander
模板里 header `ToggleButton` 的 padding + chevron 列造成的，控件自带，不是我们的 bug。

## 框架层新坑（重要，已修）：挂载期的 diff-and-write 会吞掉"写默认值"的修饰

修问题 2 时发现 `.Padding(0)` 完全无效：按钮实测还是默认样式的 `11,5,11,6`。

根因：`Reconciler.ApplyModifiers` 走 `WriteIfChanged`（与控件**当前值**比），
但控件刚 `new` 出来时读到的是**依赖属性默认值**，默认样式（Style 里的 Setter）要等
进可视树 `ApplyTemplate` 才生效。于是"声明值恰好等于默认值"（Padding=0、Margin=0、
Opacity=1、MinHeight=0、HorizontalAlignment=Stretch…）会被判成"没变化"而跳过写入，
样式一应用就把声明值盖掉。

修法（对齐官方 OneWay 描述符语义：**mount 无条件写、update 才 diff**）：
- `PropWriter` 加 `[ThreadStatic] _mountDepth` + `BeginMount()` 作用域 + `IsMounting`；
  `Set/SetRef/SetLive/SetOptional/SetWhenPresent/SetBrush/SetColorBrush` 在挂载期
  跳过比较直接写。
- `Reconciler.WriteIfChanged/WriteRefIfChanged` 同样读 `PropWriter.IsMounting`。
- `Reconciler.Build` 开头 `using var mount = PropWriter.BeginMount();`，**必须包住
  handler.Mount**（子元素在它里面递归 Build，嵌套计数）；`Patch` 路径不进作用域，
  保持 diff 语义（避免重绘与把用户状态拽回）。

验证：修完 `[link] padding=0,0,0,0 content=StackPanel` ✓。

## 01:40–02:00 设置页"限宽 + 居中" / 页面切换动画

**问题 3：卡片的最大宽度限制"没有了"**

模板是 `Grid Width="{Binding ViewportWidth, ElementName=SettingsScrollViewer}"
MaxWidth="1200" HorizontalAlignment="Center"` —— 内容块限宽 1200 **且居中**。
我们之前只写了 `MaxWidth(1200) + HAlign(Stretch)`，实测（把限宽临时改成 200 对照）：
内容块宽 200 但 `xInScroll=20`（**靠左**）——Stretch 不会把被 MaxWidth 夹窄的元素居中。
所以宽窗口下卡片贴着左边一直延伸，看着就像"没有限宽"。

试过的错误方案：给一个很大的固定 `Width`（9999）+ MaxWidth 1200 + Center —— 视口
710 时内容块仍是 1200，`x=-224` **左边缘被裁掉**（Center 不会把它夹回视口）。

**最终方案（框架层）**：新增修饰符 `.WidthToViewport()`
（`ElementModifiers.WidthToViewport`），语义 = 模板那个 `Width="{Binding ViewportWidth}"`。
由 `ScrollViewerHandler` 在挂载后把 `ScrollViewer.ViewportWidth` 同步到内容控件的
`Width`，并订阅 `SizeChanged` / `ViewChanged` / `Loaded` 持续同步；未声明该标记时解绑。
用法：`.WidthToViewport().MaxWidth(1200).HAlign(Center)`。

**两个坑**：
1. 必须写在 **ScrollViewer 的直接内容**上（handler 只认 `scroll.Content`）。
   一开始挂在内层 VStack 上，结果网格 Group 被同步、VStack 没被同步，宽度仍是 desired。
2. `FrameworkElement.Width` 默认是 **NaN**：`Math.Abs(NaN - w) > 0.5` 恒为 false，
   第一次永远写不进去。必须先 `double.IsNaN(current)` 单独判断。

**问题 4：没有 page 动画**

模板的 `ContentFrame` 靠 `Frame.Navigate` 触发 `Frame.ContentTransitions`；
我们是换 Content，同样会触发 ContentTransitions。
- `FrameElement` 新增 `Transition`（枚举 `PageTransition`：None / Entrance / DrillIn /
  SlideFromRight，默认 Entrance），`FrameHandler` 只在类型变化时重建
  `TransitionCollection`（每帧 new 会被当成"变了"重走动画初始化）。
- 注意：只有新旧页面**换了原生控件**（元素类型不同）才会替换 Content 而播动画；
  同类型元素被就地 patch 时不播——内容没换，本就不该播。

**验证**：视口 1190 时内容块铺满（1190.7）、x=20；限宽 200 对照实验下
`x = padding + (viewport-200)/2` 精确居中 ✓；无横向 extent（scrollable=0）；
自动切页一次（主页→设置页）无异常；0 错误 0 警告，核心测试 40/40；探针与
App.cs 的 PreferredLaunchViewSize 等临时改动已全部还原。

把 `ContentMaxWidth` 临时改成 100/400 做对照（窗口拉不宽：TryResizeView 返回 False、

  原生默认都是 **Disabled** —— 两处默认值不一致会让"默认构造"行为随调用点漂移。
- 补 `ScrollViewerElement.HorizontalContent`（XAML 的
  `HorizontalContentAlignment`，模板设置页显式写 Stretch）。

### 结论 2：Frame 页面动画——声明式过渡在这条路径上根本不播（三重证伪）
1. `Frame.ContentTransitions` 塞 `NavigationThemeTransition` → 换 Content 后
   新页面 Opacity 全程 1（不播）。
2. 换成 `EntranceThemeTransition` 塞 `ContentTransitions` → 同样不播。
3. 挂 `UIElement.Transitions = { EntranceThemeTransition }` → 集合确实挂上了
   （`Transitions.Count == 1`），**还是不播**。
原因：`NavigationThemeTransition` 只在 `Frame.Navigate` 的完整导航流程里被驱动；
`Frame` 也不会执行 `ContentTransitions` 集合。我们这里是直接换 `Frame.Content`。

**最终方案**：`FrameHandler` 自己起 Storyboard（Opacity 0→1 + TranslateTransform
归零，250ms，CubicEase EaseOut），并在 `Completed` 里兜底 `Opacity=1、
RenderTransform=null`（否则一次失败的动画会让整页永久透明）。
`PageTransition` 枚举含义相应改为：Entrance=上移30、DrillIn=上移80、
SlideFromRight=右移120。

### 关键教训：别用「读 DP 值」判断动画有没有播
我一开始用「采样 `element.Opacity` 是否 < 1」判断，三种方案都得到 min=1，
差点全部误判成"没播"。实际上 **Opacity 淡入是独立（合成线程）动画，DP getter
读回的是基值 1**。改用 `Storyboard.Completed` 事件验证，才看到
`entrance begin → completed` 间隔 434ms —— 动画真的在跑。
→ 以后验证动画要用 Completed / 事件，不要用属性值采样。

### 另一个坑：清理探针时误删 try 主体
用 Edit 替换大段代码时把 `try { page.RenderTransform=...; page.Opacity=0;
storyboard.Begin(); }` 整段吃掉，变成空 try（编译仍通过！）。
**改完必须回读被替换区域**，尤其是删除临时 trace 的时候。

## 03:00–03:30 从"自制机制"换成官方机制（Binding + ContentTransitions）

### 宽度：手动 SizeChanged 同步 → 真正的 XAML 绑定
之前 `.WidthToViewport()` 是"订阅 SizeChanged / ViewChanged 手动写 Width"，
`.WidthToParent()` 同理。这条路与模板的 `{Binding ViewportWidth, ElementName=...}`
不等价：手动同步要等 SizeChanged 事件，而 ScrollViewer 触发 SizeChanged 时
ViewportWidth 未必已更新（慢一拍），也会漏掉"尺寸没变但滚动条出现"的情况。
改成官方绑定：
- `ScrollViewerHandler`：`target.SetBinding(WidthProperty, new Binding {
  Source = scroll, Path = new PropertyPath("ViewportWidth"), Mode = OneWay })`
- `ParentWidthBinding`：`Source = parent, Path = "ActualWidth"`
- 用 `ConditionalWeakTable` 记录"哪个控件被绑过"，这样才有资格 ClearValue
  （否则会把应用侧 `.Width()` 设的本地值一起清掉）。
- **UWP 陷阱**：`ActualWidth` 是只读 DP，**没有属性变更通知**，绑定只在建立时求值一次
  （模板 HomePage 也是这么写的，所以模板自己在窗口缩放时也不更新）。
  补偿做法：父容器 SizeChanged 时**重新 SetBinding**（强制重新求值），
  而不是写本地值——Width 的来源始终是绑定。

验证：`[local] Width 的本地值类型 = BindingExpression`（证明不是手写的 double），
设置页 `width=710.7 == ViewportWidth`，主页 `width=750.7 == 父容器 ActualWidth`，
卡片全部 `halign=Stretch actual=710.7` 撑满。

### 动画：自制 Storyboard → 官方 Frame.ContentTransitions
改成官方集合：`Frame.ContentTransitions = { NavigationThemeTransition {
  DefaultNavigationTransitionInfo = Entrance/DrillIn/Slide } }`——就是 XAML 里
`<Frame.ContentTransitions>` 那一层，也是 Frame.Navigate 默认用的那套导航过渡。

**这一条我必须诚实标注：无法在进程内验证它是否播放。**
- 过渡是**独立（合成线程）动画**：DP getter 读回基值（Opacity 恒 1）、
  `ElementCompositionPreview.GetElementVisual(el).Opacity / Offset` 读到的也是
  UI 线程侧的基值（`minOpacity=1, offsetY delta=0`）。
  合成采样实测 ContentTransitions 与 UIElement.Transitions 两种方案结果都"没变化"，
  但这与"独立动画值不回传"完全无法区分 → **两种解读都可能，不能据此断定不播**。
- 想用 `Frame.Navigate`（真正的官方驱动路径）做对照实验也没跑成：
  **UWP 应用失焦后会被挂起，DispatcherTimer 直接停摆**，探针的有效窗口只有 ~1 秒，
  0.8s / 1.2s / 2.5s 的定时器多次根本没触发，日志断在半路。

→ 结论留给真机目视确认。若确认不播，唯一能拿到官方导航动画的办法是让页面切换
走真正的 `Frame.Navigate`（需要真实 Page 类型 + XAML 元数据），成本不小。

### 方法论教训（重要，本次连踩两次）
1. **判断"动画有没有播"不能用属性值采样**。第一层坑：DP getter 读基值。
   第二层坑：改用合成视觉 `GetElementVisual()` 读 Opacity/Offset **仍然不可靠**——
   独立动画跑在合成线程，值不回传 UI 线程。
   唯一可靠的进程内信号是 **Storyboard.Completed 这类事件**，而 theme transition
   没有 Completed。所以声明式过渡只能目视验证。
2. **UWP 诊断探针的可用窗口只有约 1 秒**：应用一失焦就被挂起，DispatcherTimer 停摆。
   长周期采样（几秒）的实验设计在这里不成立，要改成"启动后 300ms 采一次"。

  `PageTransition` 只负责挑 `NavigationTransitionInfo`（None → `Suppress`，Entrance
  → `Entrance`，DrillIn → `DrillIn`，SlideFromRight → `Slide FromRight`），
  建好的元素树注入 `Page.Content`。实测可视树里出现 `Page` 节点 = 路径生效。

### 参考项目（WinUI3 官方 Reactor）的做法，备查
`src/Reactor/Core/Navigation/TransitionEngine.cs`：它**确实**是在合成层重放
WinUI 动作（Entrance 位移 140px / 出 150ms / 入 300ms，缓动 0.1,0.9,0.2,1），
并 gate 在 `UISettings.AnimationsEnabled` 上。注释写明原因：Reactor 内部导航
不能用 Frame.Navigate，所以自己重放。我们 UWP 侧能用真 Navigate，就不必重放。

### 方法论补记（推翻 09-27 前半段的悲观结论）
- UWP 探针**不是**只有 1 秒窗口：用 `diag-run.ps1`（Start-Process shell:AppsFolder）
  启动后 app 是前台的，DispatcherTimer 能连续跑满 1~1.5 秒，30ms 间隔采样可行。
- 判断"有没有播"依然不能用属性采样（DP 读基值、`GetElementVisual().Opacity`
  对独立动画也读不到；`RenderTargetBitmap` 在这台机器上 `GetPixelsAsync()` 返回
  长度 0）。
- **可靠的验证手段是遍历可视树读 `ActualWidth / MaxWidth / HorizontalAlignment`**
  （用 DispatcherTimer 延迟 ~1.2s 后打印）——这次就是靠它同时验掉了"限宽"和
  "Page 节点存在（= 走了 Navigate）"。
