## 真正根因（第二轮，自检全绿后定位）

- 运行时自检全绿（OS 26200 / acrylicApi ok / mica ok / transparent ok / 节电 NO /
  高对比 NO / active ok），说明不是系统策略，是代码结构问题。
- **根因 1（决定性）**：`ReactorHost.Root` 是 `ContentControl`，而 UWP
  `ContentControl` 的默认模板（SDK generic.xaml 第 7399 行起）只有 `ContentPresenter`，
  **没有任何元素 TemplateBinding 到 Background** → 设 `Root.Background` 完全不渲染。
  `Control.Background` 官方备注："只影响模板把 Background 用作模板 UI 属性输入的控制项"。
- **根因 2（类型约束）**：WinUI2 的
  `BackdropMaterial.SetApplyToRootOrPageBackground` 签名是 `(Control, bool)`，
  **只接受 Control**，`Grid`/`Border` 传不进去（会 CS1503）。
  所以不能简单把 Root 换成 Grid。
- 解法（两层结构）：外层保留 `ContentControl`（挂 Mica 附加属性），
  内层新增 `private readonly Grid _contentLayer` 作为 `Root.Content`，
  AcrylicBrush 挂 `_contentLayer.Background`，组件树挂 `_contentLayer.Children`。
  构建 0 错误。
- 教训：**UWP 里给控件设 Background 之前，先确认它的默认模板有没有绑定 Background**。
  Grid/Border 一定渲染；ContentControl 不渲染。

## 第三轮：对齐参考实现 Furry-Xiyi/UWP-Blank-Template（最终方案）

- 参考仓库 App.xaml.cs 的 `AppThemeManager.ApplyMaterial` 给出正解：
  **`Window.Current.Content` 用 `Frame`**，而不是 ContentControl：
  ```csharp
  Frame rootFrame = new Frame();
  Window.Current.Content = rootFrame;
  // 亚克力
  rootFrame.Background = new AcrylicBrush {
      BackgroundSource = AcrylicBackgroundSource.HostBackdrop,
      TintColor = tint, TintOpacity = 0.8, FallbackColor = tint };
  // Mica
  BackdropMaterial.SetApplyToRootOrPageBackground(rootFrame, true);
  rootFrame.Background = null;
  ```
- 为什么是 Frame（generic.xaml 实证）：
  - ContentControl 模板（7399 行）ContentPresenter **无 Background 绑定** → 亚克力不渲染；
  - Frame 模板（13643 行）ContentPresenter 有
    `Background="{TemplateBinding Background}"` 和 `Padding="{TemplateBinding Padding}"`；
  - Frame 继承 ContentControl → 是 Control → 满足 BackdropMaterial 的 `(Control, bool)` 签名。
  **一个元素同时满足两个约束，不需要两层结构**（上一轮的两层 Grid 方案已废弃）。
- 参考实现还做了标题栏扩展（`CoreApplicationViewTitleBar.ExtendViewIntoTitleBar = true`
  + `ApplicationView.TitleBar.ButtonBackgroundColor = Colors.Transparent`），
  否则标题栏是一条纯色带；内容下移用根 Frame 的 Padding（顶栏高度）。
- 亚克力参数照抄参考实现：TintOpacity 0.8、tint/fallback 按明暗主题取
  `#202020` / `#F3F3F3`、**不设** TintLuminosityOpacity（系统自动推算），
  并监听 `ActualThemeChanged` 刷新 tint。
- 最终改动文件：`ReactorHost.cs`（Root 改 Frame + 主题自适应 tint）、
  `ReactorApplication.cs`（新增 `ExtendIntoTitleBar`）。构建 0 错误 3 警告。

**② 横条进度条改 WinUI 2**
`ProgressHandler` 的 `ProgressBar` → `MuxControls.ProgressBar`，与 ProgressRing 统一走 WinUI2
（上一轮笔记里"ProgressBar 用 UWP 原生即可"的结论作废）。

**③ 子节点重排收尾不收敛（natives=4 expected=3 的直接来源）**
旧逻辑：逐个 `if (panel.Children.Contains(target)) { Remove(target); Insert(newIdx, target); }`。
一旦面板里出现同一控件的两份引用（上一轮错位残留），`Remove` 只删第一个、HashSet 去重又让
多余的副本不在 `toRemove` 里 → 永远删不干净，每帧重建整段 StackPanel → 布局跳动/闪烁。
改为确定性两阶段：
- 先算 `finalOrder`，并对 null / 重复复用**补建新控件**（同一个 UIElement 插两次会抛"已有逻辑父级"）；
- 再按"需求份数"倒序删除多余控件（含富余重复副本）；
- 最后**逐位对齐**：`i` 处若不是目标就 `RemoveAt(current)` + `Insert(i, target)`，
  不变量是"处理完 i 后前缀恒等于 finalOrder 前缀"，后续只在下标 ≥ i+1 处增删 → 必然收敛。
诊断也加强了：数量不符时打印 `old=[...] new=[...]` 的类型+Key 序列。

**④ 重入保护只覆盖一半**
`Reconciler._inRenderPass` 只在子组件自己重渲染（RunPass）时置位，
**宿主驱动的整轮渲染从不置位** → patch 途中控件事件同步回调触发的子组件更新会被判成"非重入"而立刻执行。
→ `RunPass` 改 internal + 加 `InRenderPass` 属性；`ReactorHost.Rerender` 整个包进
`_reconciler.RunPass(...)`，删掉 host 自己的 `_inRenderPass`，`RequestRerender` 改判 `_reconciler.InRenderPass`。

**⑤ NavigationView 每帧写回 IsPaneOpen → pane 反复开合闪烁**
`Update` 里无条件 `control.IsPaneOpen = newElement.IsPaneOpen` 会把用户/控件的开合状态拽回来。
改为只在 `oldElement.X != newElement.X` 时写（Header / IsPaneOpen / IsSettingsVisible）；
`SelectedItem` 也只在 `SelectedIndex` 真的变了才回写，避免 SelectionChanged→setState 回环。
ListView/GridView 的 Header / SelectionMode 同样改成条件写。

**⑥ 布局：列表显式限高**
ListView `.Height(150)`、GridView `.Height(120)`、Image `.Width(96).Height(96)` ——
列表在垂直 StackPanel 里按内容撑开，选中/重排时高度抖动会顶动下方内容。

**踩坑**：UWP 的 `ScrollViewer` **继承 `ContentControl`**（不是直接继承 Control），
所以我一度以为"`PatchSingleChild` 漏了 ScrollViewer 分支导致整页不更新"是错的 ——
编译器直接报 CS8510「该模式不可访问」帮我否掉了这个猜测。

## WinRT 集合投影层（用户首跑模板页崩溃 0xc000027b 后补）
崩溃：`BreadcrumbBar.ItemsSource = List<string>` →
`ArgumentException: Argument 'source' is not a supported vector.`（未处理异常 → 进程终止）。
**根因**：WinUI 2 的 ItemsSourceView 只接受 `IVector<IInspectable>` /
`IObservableVector<IInspectable>`；CsWinRT 把 `List<string>` 投影成 `IVector<HSTRING>`，被拒。
该消息字符串在本机 WinRT.Runtime.dll / SDK 里都搜不到 → 来自 WinUI 2 原生侧校验。
模板仓库能跑是因为它用 `ObservableCollection<string>` + `{x:Bind}`（x:Bind 编译期也是直接赋值）。

新增 `Reactor.uwp/Internal/WinRtValue.cs`（值 → WinRT 属性 的投影层）：
- `TryAssignItemsSource(assign, source, what)`：候选链依次尝试
  `原IList<object>` → `ObservableCollection<string>` → `ObservableCollection<object>`
  → `List<object>` → `object[]`，每个都 try/catch；全失败则置空 + Trace，**不再让进程崩**。
- `Project(value)`：字符串/UIElement 原样，集合走向量投影。
- BreadcrumbBar handler 已改走该层（不再 `Items?.ToList()`）。

**二轮实测校正**：候选链里 5 种容器（string[] / ObservableCollection&lt;string&gt; /
ObservableCollection&lt;object&gt; / List&lt;object&gt; / object[]）**全被拒**，
说明与元素类型无关——CsWinRT 给托管集合建的 CCW 整体上不被 WinUI 2 的 ItemsSourceView 接受。
因此 BreadcrumbBar 改双路径：
- 静态能力探测 `ProbeItemsSource()`（静默，失败则记一行日志）；
- 探测通过 → 原生 `MuxControls.BreadcrumbBar`；
- 否则 → `BuildFallback()`：横向 StackPanel + TextBlock(CaptionTextBlockStyle) + "›" 分隔符，
  零 ABI 依赖，视觉等价。handler 基类随之改为 `ElementHandler<BreadcrumbBarElement, FrameworkElement>`。
**结论（可复用）**：本环境（OS 26200 / WinUI 2.8.7 / net10 UWP）下，
**任何托管集合都不能直接赋给 WinUI 2 控件的 `object` 型集合属性**；
需要集合语义时要么自建控件渲染，要么造真正的 WinRT 向量。

**原生 E_FAIL 的定位手段**（点进设置页后 `COMException 未指定的错误`，堆栈为空 → 来自 XAML 原生侧）：
- `OnUnhandledException` 里对 COMException 临时 `e.Handled = true`（去重、同条最多吞 5 次），
  让进程活着，一次运行能收集多个问题；生产定位后应改回不吞。
- 吞掉时 `DumpVisualTree()`：递归打可视树（深度 ≤8、8000 字符封顶），
  用来发现重复挂载 / 缺模板的控件——原生异常没有托管堆栈，只能靠这个。
- `Reconciler.Patch` 包 try/catch：记 `old -> next 元素类型 + native 类型 + 堆栈` 后原样抛。
- `Reconciler.Build` 打一行 `[reactor] build XxxElement`：崩溃前最后一个 build 的元素 = 嫌疑区域。
- `ReactorHost.Rerender` 末尾 `Root.UpdateLayout()` 包 try/catch：把原生布局异常拉进托管帧，
  堆栈里能看出是布局阶段（**诊断用，定位后删**：每次渲染强制布局有性能代价）。
- 可视树快照加深到 depth≤16 / 20000 字符，并标注 Visibility。
注：吞异常后进程仍以 0xc000027b 退出过一次 —— UWP 的 fail-fast 不一定被 `e.Handled` 拦住。

## 真正的崩溃根因（2026-09-26 22:0x，本轮定位到并修复）

**不是集合投影，是漏登记第三方控件库的 XamlMetadataProvider。**

- 证据链：把 `BlankTemplateApp` 初始页临时改成设置页（无人值守复现，不用手点），
  启动即 `UNHANDLED EXCEPTION 0x80004005 未指定的错误` → 进程死；
  可视树里 `ScrollViewer/ScrollContentPresenter` **没有任何子节点**（模板没套上就炸了）。
  主页（不含 Toolkit 控件）从不崩。
- 根因：有 App.xaml 时，XAML 编译器生成的 `App.g.i.cs` 会把**所有**引用控件库的
  `IXamlMetadataProvider` 串起来；我们是纯代码入口（无 App.xaml），只手写了 MUX 那一个。
  Toolkit 的 SettingsCard/SettingsExpander 首次套模板时，XAML 按名字向 Application 查
  `IXamlMetadataProvider` → null → 原生抛 E_FAIL("未指定的错误") + fast-fail(0xc000027b)，
  `e.Handled = true` 拦不住。**症状与"集合投影写错"一模一样，以后先查这里。**
- 修复：`ReactorApplication` 改成**链式查询**的 `List<IXamlMetadataProvider>`：
  1. `Microsoft.UI.Xaml.XamlTypeInfo.XamlControlsXamlMetaDataProvider`（WinUI 2）
  2. `CommunityToolkit.WinUI.Controls.SettingsControlsRns
     .CommunityToolkit_WinUI_Controls_SettingsControls_XamlTypeInfo.XamlMetaDataProvider`
     （CsWinRT 给 WinRT 组件生成的怪命名空间，从包内 .xml 的 `T:` 条目能查到全名）
  并暴露 `RegisterXamlMetadataProvider(...)` 供以后加库。
  → 设置页 mount + home↔settings 往返 patch 均不再崩，进程存活。

**顺带修掉的两处**：
1. BreadcrumbBar **彻底不用原生控件**（原生 ItemsSource 的 CCW 在布局期才会炸，
   赋值时不报错，是最阴的一种）：改为自建 StackPanel + "›" 分隔符 + `Tapped` 回 index，
   handler 基类收敛成 `ElementHandler<BreadcrumbBarElement, StackPanel>`。
2. `SingleChildAccessor`（新增，注册表式，无反射）：Toolkit `SettingsExpander`
   **不继承 ContentControl**（SettingsCard 继承，所以只有 Expander 有问题），
   `PatchSingleChild` 认不出来 → 每轮重渲染都整棵子树重建（日志刷
   `单子元素容器不支持就地更新`）。登记访问器后就地 patch，告警消失。

**定位手段升级（可复用）**：
- `ReactorHost` 强制 `Root.UpdateLayout()` 抛错后，跑 `LocateLayoutFailure`：
  **逐层二分**——把子树的 `Visibility` 临时置 Collapsed 再跑根布局，不抛了就说明元凶在里面，
  继续往下钻。比"逐节点 Measure"（实测复现不出来）可靠。

## 设置页"展开卡片就撑到最大宽度"（已定位 + 修复）

- 现象（用户报告）：折叠时卡片窄，一展开任意 SettingsExpander 就跳到很宽。
- 实测（临时探针，每秒采样 ActualWidth，第 3 秒程序展开全部卡片）：
  折叠 `stack=222.67 / cards=222.67` → 展开 `stack=1000 / cards=1000`。
- **根因**：ScrollViewer 只要**横向可滚动**（`HorizontalScrollBarVisibility != Disabled`），
  就用**无限宽**测量内容 → 子元素的 `Stretch` 退化为"按内容收缩"，宽度取决于最宽子项。
  SettingsExpander 展开后内部的 ItemsRepeater 同样按无限宽测量 → 期望宽暴涨 →
  被 StackPanel 的 `MaxWidth=1000` 封顶 → 整栈从 222 跳到 1000。
  参考仓库 `SettingsPage.xaml` 用 `[Grid 包裹 StackPanel]` 的注释就是在防这类 ItemsRepeater
  视觉故障，但只包 Grid 挡不住宽度漂移。
- **修复**：`ScrollViewerElement` 新增 `HorizontalScrollBar / VerticalScrollBar /
  HorizontalScroll / VerticalScroll`（默认仍是 Auto/Enabled，不影响既有用法），
  handler 在 Mount+Update 都写；设置页传
  `horizontalScrollBar: Disabled, horizontalScroll: Disabled`。
  关掉横向滚动 → 内容按**视口宽**测量 → 宽度稳定 = min(视口, MaxWidth)。
- 复测：窗口 540 宽下，折叠与展开**都是 178.67**，9 次采样零漂移；进程无异常。
- 排查方法沉淀：**别猜宽度问题，直接每秒采 ActualWidth**（DispatcherTimer +
  VisualTreeHelper 收集目标类型 + 必要时程序改状态触发目标场景），一次运行就能拿到数字。
- 坑：`App.OnLaunched` 的 override **不会被框架调用**（基类 ReactorApplication 里那个才会），
  临时诊断代码要挂在组件 `Render()` 里（UI 线程）才跑得起来。

### 追问"参考实现咋解决的"→ 对齐官方默认值策略（已改）

查官方 `microsoft-ui-reactor` 源码得到三层答案：
1. **纵向列表显式禁横滚**（最贴近场景，`src/Reactor/Core/V1Protocol/LazyStackLifecycle.cs`）：
   `sv.HorizontalScrollBarVisibility = orientation == Horizontal ? Auto : Disabled;`
   （纵向列表 → 横向 Disabled；Vertical 反向）。官方虚拟列表也是这么避免无限宽测量的。
2. **元素默认值是公开契约**：`ScrollViewerElement`（Element.cs:4545）的 5 个滚动 enum 是
   非 nullable + 带默认值，生成器判为 `Unconditional` → `.OneWay` **无条件写**（默认 Auto）；
   但它是 record 的 init 默认值，调用方可 `with { HorizontalScrollBarVisibility = Disabled }` 覆盖
   （gallery 的 "Classic ScrollViewer" 示例正是这么写的，ScrollMode 也一起禁）。
3. **生成器分层的默认值语义**（`WrapperGenerator.cs` 1126~1660）：
   - 非 nullable 值类型（元素语义必需，如 Child/Orientation）→ 无条件写；
   - `T?` / `Optional<T>` → `OneWayConditional`，**未设置就不写**，`Optional.Unset` 还会
     `ClearValue(dp)` 还原控件原生默认。
   → 官方把"偏离原生默认"的风险压在少数几个属性里，且默认值显式可见、可覆盖。
   对比：我们上一版把 Auto 硬编码在 **handler 内部**，调用方连改的口子都没有 —— 这才是病根。

**已改**：`ScrollViewerElement` 默认 `HorizontalScrollBar = Disabled`（对齐原生/XAML 裸写
`<ScrollViewer>` 的默认：Vertical=Auto + Horizontal=Disabled），参数仍可显式覆盖。
设置页里显式传的两个 Disabled 保持不变（无害，等于把默认写明白）。
影响面：`UwpApp` 只有 3 处 `ScrollViewer(...)`（设置页 / CoreLoopRegression / ElementGallery）。
构建 0 错误，启动 14 秒无异常日志。

**原则（以后新增元素照此办）**：框架元素的默认值 == 该控件在 XAML 里的原生默认值；
凡是会改变测量/布局语义的属性（滚动轴、对齐、Stretch），默认值尤其不能自己发明。

### 追问"参考项目怎么做的"→ 官方防重建的三层机制（只读源码，未改代码）

官方 `Microsoft.UI.Reactor` 用 **descriptor（属性绑定表）** 而不是手写 handler，
从机制上消除了"无条件写 / 整体重建"：

1. **值属性 = diff-and-write**（`Core/V1Protocol/Descriptor/PropEntry.cs` 的
   `OneWayPropEntry.Update`）：
   `if (!_comparer.Equals(_get(oldEl), nv)) _set(ctrl, nv);`
   默认 `EqualityComparer<TValue>.Default`。→ **值没变就不写**，根本不会有"写同值触发重绘"。
   另有 `OneWayConditional`（未设置不写 / `Optional.Unset` → `ClearValue(dp)` 还原控件默认）、
   `Initial`/`InitialOnly`（只在 mount 写一次，之后值归控件自己 —— 适合"种子值"属性）。
2. **UIElement 派生的一律不是值属性**（`WrapperGenerator.cs`
   `IsSupportedReference`：沿基类链查到 `UIElement` 就 return false，注释写明
   "Border.Child, IconElement, … are content slots"）→ 走**内容槽** → 走 patch 复用。
   → 我们把 SettingsCard 的 HeaderIcon 当"值"每次 `BuildIcon` 重建，属于**分类错误**。
3. **用户可改的双向属性 = `Controlled`**（`get/set/subscribe/callback/readBack`）
   + `ChangeEchoSuppressor` / `ExpectedEcho` **回声抑制**：框架写入前记下"期望回读值"，
   控件随后的事件若回读出该值就判定为回声、不再回调用户、也不回写
   （`ExpanderElement` 的 `IsExpanded` 就是 counter-echo HandCodedControlled over
   Expanding + Collapsed）。
   → 这才是"用户手动展开不会被重渲染拽回"的正解；我们目前的"条件写"只是弱化版。

**对我们框架的迁移结论**：手写 handler 缺一层统一的 diff/内容槽机制，靠每个 handler
自觉写 `if (old != new)` 迟早漏。下一步可加 `ElementHandler.SetIfChanged(old, new, set)`
统一入口，并把 IconElement/UIElement 类属性从"值"改判为"内容槽"。

## 「和官方对齐」落地：三层写入机制已搬进手写 handler 架构

**新增文件**
- `Reactor.uwp/Internal/PropWriter.cs`：官方 `ControlDescriptor` 的三档绑定语义
  —— `Set`（OneWay：old==new 不写）、`SetRef`（引用比较，用于 Brush/Style）、
  `SetLive`（与控件当前值比，用于会被 clamp 的属性如 Slider.Value）、
  `SetOptional`（`Optional.Unset` → `ClearValue(dp)` 还原原生默认）、
  `SetBrush`（Brush 先比引用再比"纯色比颜色"）、`SetColorBrush`、`SequenceEqual`。
- `Reactor.uwp/Internal/EchoGuard.cs`：回声抑制。写入前 `Expect(control, v)`，
  事件里 `Consume(control, v)` 命中就是不回调。带 1 秒有效期兜底——
  **宁可多回调一次也不能丢用户事件**（陈旧期望不得误吞真实操作）。

**改造**
- 全部 handler 的 Update 不再直接 `control.X = v`，一律走 `PropWriter`。
- `SettingsCardHandlerBase`：**HeaderIcon 从"值"改判为"内容槽"**，用 `IconSlots`
  字典缓存已挂载图标；同类型描述 → `reconciler.Patch` 复用控件，类型变了才重建。
  这是官方 `IsSupportedReference` 那条规则（UIElement 派生 = 内容槽）的落地。
- `Reconciler.ApplyModifiers`：所有修饰符改成 `WriteIfChanged` / `WriteRefIfChanged`
  （与控件当前值比）。Brush 不再每帧 `new SolidColorBrush`。
- `GridHandler`：`GridDefinition` 是 record 但字段是**数组**，默认 Equals 走引用比较
  → 每帧都判"变了" → Clear + 重建行列定义 → 整个 Grid 重排。改成结构比较
  （`SameDefinition` 逐轨道比）。
- 受控属性全部加回声抑制：TextBox.Text / CheckBox.IsChecked / Slider.Value /
  ComboBox.SelectedIndex / RadioButtons.SelectedIndex / ToggleSwitch.IsOn /
  NavigationView.SelectedItem（含 **mount 首次写入也要 Expect**，否则启动瞬间会
  回调一次把初始页改掉）。
- `InfoBar.IsOpen` 改成官方 Initial 语义：只在 mount 写，用户关掉后不被拽回。

**实测（探针：每秒采可视树图标 HashCode + 程序点击开关）**
- 8 个 FontIcon / 1 BitmapIcon 的 HashCode 在 9 次采样、3 次重渲染、2 次点击后
  **全程不变**（改造前每点一次开关重建 5 个图标）。
- 每次点击后的新增 build = **0**。
- 构建 0 错误 0 警告，核心测试 40/40，进程存活无异常。

**原则（新增元素照此办）**
1. 值属性走 `PropWriter.Set`；引用类型（Brush/Style/ImageSource）走 `SetRef`。
2. UIElement 派生的属性（IconElement / Child / Content）一律当内容槽，patch 复用。
3. 用户可改的双向属性 = 条件写 + `EchoGuard`。
4. 集合型 record 字段（数组、委托）默认 Equals 不可靠，必须自己写结构比较。

## 23:40–00:05 面包屑尺寸 / 卡片组间隔 / ContentDialog 弹窗

**根因 1：抽象尺寸（Padding）支持缺档** → `Reconciler.ApplyModifiers` 只把
`.Padding()` 写到 `Control` / `TextBlock`，而 UWP 里 Padding 是各类型各自声明的：
`StackPanel` / `Grid` / `RelativePanel` / `Border` / `ContentPresenter` 都有，
`Panel` 基类**没有**（`Canvas` / `Viewbox` 也没有）。所以 `HStack(...).Padding(...)`
被静默丢弃。已补齐 + 对无该属性的类型按类型只报一次日志
（`UnsupportedPaddingTypes`）。同理 `.FontSize()` 补了 `FontIcon` 分支
（IconElement 既不是 Control 也不是 TextBlock）。

**根因 2：组间距被依赖属性优先级吃掉** → 节标题同时写了"样式里的 Margin(0,32,0,8)"
和"本地 `.Margin(0,0,0,8)`"，本地值压过样式值，32px 上边距整个消失，只剩
StackPanel 的 4px。教训：**同一个属性不要在样式和本地修饰符里各写一次**。
已改成模板结构：外层 `VStack(32)`（组间距）+ 每组 `VStack(3)` + 节标题
14px SemiBold / 下边距 6（边距只放样式里）。

**根因 3：面包屑尺寸** → 模板 `MainPage.xaml` 的 BreadcrumbBar ItemTemplate 是
`SubtitleTextBlockStyle` + `FontSize=28`，我们的自建实现写死 Caption(12px)。
`BreadcrumbBarElement` 新增 `ItemFontSize` / `ItemStyleKey`；外层对齐
`Spacing=4` + `Padding(20,16,20,0)`（这个 padding 之前正是被根因 1 丢掉的）。

**新增：ContentDialog 弹窗** → `ContentDialogElement` + `ReactorDialog.ShowAsync`。
**不注册 handler**（弹窗不能进可视树，Panel.Children 里放 ContentDialog 会让
ShowAsync 失败），走独立构建路径：`new Reconciler().Build(content)`。
UWP 同时只允许一个弹窗 → 静态闸门 + 失败记日志返回 None。用法对齐模板
`Dialogs/ExternalOpenDialog`：外链点击 → 弹"此应用尝试打开外部应用 / 是否允许？"
主按钮"是"、次按钮"否"、`DefaultButton=Secondary`、样式 `DefaultContentDialogStyle`。

**验证**：0 错误（2 个 MSB3277 是 WebView2/WPF 的既有警告，与本次无关），
核心测试 40/40；临时把初始页切成设置页跑了一次冒烟，进程存活、日志无异常、
无"未找到命名样式 / 被忽略"记录（说明 SubtitleTextBlockStyle 命中、Padding 已生效）。

**原则（补充）**
5. 修饰符要落到"属性是否真的存在于该原生类型"上：`Panel` 没有 Padding，
   `FontIcon` 不是 Control——写错就是静默丢弃，必须按类型穷举 + 一次性告警。
6. 弹窗类（ContentDialog / Popup 家族）不进协调器的父子树，走独立构建 + 命令式显示。
